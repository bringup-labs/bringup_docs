# Bringup Docs Refactor — Design

**Date:** 2026-07-25
**Status:** Approved, ready for implementation planning

## Problem

The docs describe **Bagmaster** as "the core data platform for recording, managing,
visualizing, and analyzing ROS bags at scale." That was true once. It is not true now.

Bag Master is today **one of eleven extensions** (`ext_data`, v0.1.0) inside the Bringup
desktop app (`bringup-app` v0.4.1) — an Electron workbench with a privileged daemon, an
extension host, and a marketplace. The docs do not describe the product any more; they
describe a component of it.

Concrete defects in the current site:

- `index.mdx` positions Bagmaster as the whole platform.
- All six `DocsOverview` cards link to `/getting-started`, **which does not exist** —
  every card on the landing page is a dead link.
- One card links to `github.com/bringup-labs/bagmaster/discussions`.
- `editUrl` points at `bringup-labs/bagmaster_docs`; the real repo is
  `bringup-labs/bringup_docs`.
- `tagline` reads "ROS Bag Management and Visualization Platform".
- The footer's only Documentation link is the dead `/getting-started`.

## Non-goals

- Rewriting the flow-reference content. It is substantively accurate (3,251 lines,
  task types like `dev.bringup.plugin.core.shell.Shell` match current plugin naming).
  It gets **re-homed and de-Bagmastered**, not rewritten.
- Replacing the Docusaurus scaffolding, theme, search, PWA, or mermaid setup.
- Extension-developer documentation. `bringup_desktop_app/docs/extensions-platform.md`
  and `multi-target-extensions.md` stay where they are. Deferred, not cancelled.
- Setting the Google Analytics ID. `gtag.trackingID` is still the `G-XXXXXXXXXX`
  placeholder; that value is the maintainers' to supply.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Task-centric tutorials as the spine, **plus** per-extension reference pages | Users arrive with a job to do, not an extension to learn — but they still need a place to look up what each extension does. |
| 2 | Four top-level sections + FAQ | Separates learning from lookup; sidebar reads as a curriculum. |
| 3 | Screenshots generated by a scripted Playwright run, with seeded fake data | Reproducible, regenerable as the UI changes, and exposes no real org or device data. |
| 4 | Broad FAQ including product/commercial questions | Requested. Commercial answers are sourced from `bringup.dev/pricing`, not invented. |
| 5 | Spec lives in `specs/`, **not** `docs/` | `docs/` is the Docusaurus content root with `routeBasePath: '/'` — a spec placed there would be published to the live site. |

## Grounding facts

Verified against the repo and the live site. Docs must match these.

**Product positioning** (bringup.dev): tagline "The operating layer for robotics
development."; hero "One platform for the entire robotics lifecycle — data, secure
access, CI, and fleet operations."; offline-first, zero-trust, no inbound ports on
robots, source-available.

**Downloads:** `https://bringup.dev/download`. The page does not expose per-platform
file URLs, so `install.md` links to the download page rather than to build artifacts.
Release artifacts are published to the `bringup-releases` bucket at
`https://storage.bringup.dev`, which is release plumbing, not a user-facing URL.

**Device onboarding** (`ext_fleet/src/webview/views/AddRobotModal.tsx:218-219`):

```bash
curl -fsSL https://bringup.dev/device.sh | sudo bash
sudo bringup register --setup-key <key> --hostname <hostname> --device-type <type>
```

A `--setup-key-stdin` variant exists for piping (`register.go:209-212`).

**Desktop onboarding** (`WelcomeScreen.tsx`): two steps — Welcome → daemon setup. The
daemon is a privileged system service, which is why the OS prompts for an admin password.

**Workbench shape** (`WorkbenchCore.tsx`): activity bar → sidebar (`labeled` 220px /
`rail` 52px, persisted in `localStorage` as `bu-sidebar-mode`) → view router → bottom
panel, plus a command palette and terminal.

**Extensions** (`ExtensionsPanel.tsx`): sources are `builtin | repo | bundled | local |
marketplace`; each declares permissions; install targets are `desktop | controller |
agent`; workspaces carry a trust flag.

**The eleven extensions:** Fleet Manager (0.2.14), Organization Manager (0.2.9), Shell
Access (0.1.7), File Browser (0.1.3), Telemetry (0.1.8), Visualizer (0.2.0), Zenoh
Bridge (0.1.1), Image Deploy (0.1.0), Yocto Builder (0.1.0), Rollouts (0.1.0), Bag
Master (0.1.0).

**Pricing** (bringup.dev/pricing): Personal — free, available today. Team — per seat,
price announced at launch, billed per organization. Enterprise & Self-Host — custom,
license-based, self-host cloud/on-prem/air-gapped. The docs link to `/pricing` as the
source of truth rather than restating figures that will drift.

## Screenshots

A new `e2e/screenshots.spec.ts` in `bringup_desktop_app` reuses the existing
`e2e/fixtures.ts` and `buildSignedInSecrets()` harness, seeds fake devices and orgs, and
writes PNGs to `bringup_docs/docs/assets/screenshots/`.

Verified feasible: `npx playwright test e2e/launch.spec.ts` passes 3/3 in 9.9s against
the current build.

Planned captures: welcome screen · daemon setup step · workbench (labeled and rail
sidebar) · command palette · extensions panel · marketplace · trust dialog · settings ·
terminal panel · device inventory · device detail.

`ext_fleet/tools/docker-robot/` runs a fake robot in Docker and may allow a genuinely
populated fleet view. Worth attempting; not a blocker.

**Rule:** where the harness cannot populate a view, the page ships **without** a
screenshot. No mocked-up images of screens that were never rendered.

## FAQ

Three groups in `faq.md`:

1. **Getting started & concepts** — what Bringup is, what the daemon is, what extensions
   are, supported platforms, offline behaviour.
2. **Troubleshooting** — admin password prompt, daemon won't start, device won't come
   online, where logs and config live, update channels, extension trust prompts,
   uninstalling the system service. All traceable to README or source.
3. **Product & commercial** — pricing tiers, licensing, self-hosting, support. Sourced
   from bringup.dev/pricing, each linking out to the live page.

Any question that cannot be answered from the repo or the live site is written with the
question posed and a clearly-marked `TODO` for the maintainers, never a guessed answer.

## Preserved vs. rewritten

**Preserved:** all 3,251 lines of flow-reference content and its 4 screenshots; the
Docusaurus scaffolding; `CollapsibleSection`; PWA, local search, and mermaid config; the
`anchor-reveal` client module; `custom.css`.

**Rewritten.** Full inventory of Bagmaster references, counted:

|---|---|---|

| `docs/flow-reference/guides/flow-creation-guide.md` | 7 | Retarget to Bag Master extension |
| `docs/flow-reference/Plugins/rosbag-loader.md` | 6 | Retarget |

**Package rename is coupled and can break the build.** Root `package.json` is
`bagmaster-documentation-monorepo`; `website/package.json` is `bagmaster-website`; and
five root scripts invoke `pnpm --filter bagmaster-website`. Renaming the website package
without updating every filter silently breaks `start`, `build`, `build:fast`, `serve`,
and `docusaurus`. Rename and filters must change in the same commit, verified by running
`pnpm build`.

## Known gaps

Stated rather than papered over.

1. **Cloud-backed extension pages will be thinner.** Rollouts, Organization Manager, and
   Telemetry cannot be exercised against a live backend from this environment. Those
   pages are written from source and marked where behaviour was not observed running.
2. **No per-platform download URLs.** `install.md` points at `bringup.dev/download`.
3. **Windows.** `electron-builder` and CI build for Windows, and the README documents
   Windows config and log paths, but the daemon uninstall instructions cover only macOS
   and Linux. Docs will state Windows support as-built and not invent uninstall steps.

## Implementation phasing

Each phase leaves the site building and deployable, so work can stop between phases.

1. **Rename and unblock** — config strings, package renames with pnpm filters,
   `DocsOverview` rewrite, `index.mdx`. Kills every dead link. Verify: `pnpm build`.
2. **Re-home flow-reference** — move under `extensions/bag-master/`, fix the 20
   Bagmaster references, keep the 4 existing screenshots working.
3. **Get Started + Tutorials** — the seven journey pages.
4. **Screenshots** — `e2e/screenshots.spec.ts`, generate and commit PNGs, wire into
   pages written in phases 3 and 5.
5. **Extension reference** — eleven pages.
6. **Reference + FAQ**.

## Success criteria

1. No occurrence of "Bagmaster" as a product name anywhere in `docs/` or `website/`;
   "Bag Master" appears only as the extension.
2. Every internal link resolves — specifically, zero links to `/getting-started`.
3. `pnpm build` from the repo root completes without new broken-link warnings.
4. All eleven extensions have a reference page.
5. Screenshots are regenerable by one command, and every committed PNG was produced by
   an actual app run.
6. Every commercial claim links to bringup.dev rather than restating a figure.
